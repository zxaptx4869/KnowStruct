# OpenSpec 前置准备基线

## 0. 文档说明

### 0.1 文档目的

本文件用于在项目进入 OpenSpec 功能开发流程前，统一整理产品级背景、范围、优先级、信息架构、交互基线、领域模型、技术约束和验收标准。

它解决两个问题：

1. 为后续每个 OpenSpec Change 提供稳定的全局上下文。
2. 判断某个功能是否已经准备好进入 `proposal -> specs -> design -> tasks -> apply` 流程。

本文件不是详细 PRD，也不要求开发前填完所有远期功能。未确定内容可以保留“待补充”，但进入首个 OpenSpec Change 前，标记为“阻塞”的项目必须明确。

### 0.2 使用方式

- 已确定内容直接填写，并注明依据。
- 尚未确定的内容保留 `_待补充_`，不要用未经验证的内容强行填满。
- 产品级共识写在本文件；单个功能的行为和技术方案写入 OpenSpec Change。
- 当全局导航、核心对象或产品原则变化时，先更新本文件，再更新受影响的 OpenSpec Specs。
- 其他项目可以复制本文件，保留目录后重新填写。

### 0.3 状态标记

| 标记 | 含义 |
|---|---|
| 已确认 | 已形成明确决定，可以作为开发约束 |
| 草案 | 有初步方向，需要在开发前确认 |
| 待补充 | 当前没有足够信息 |
| 不适用 | 当前项目不需要 |

将零散经验、截图、链接、商品信息和个人记录，通过 AI 辅助整理为可维护、可检索、可审查、可追溯的结构化知识，并沉淀最终决策。

**明确不服务的用户：**

_待补充_

### 2.5 核心结果

用户能够把一份零散资料转换为经过人工确认、可以追溯来源、能够参与后续搜索和决策的正式知识记录。

状态：已确认。

### 2.6 产品成功信号

**核心成功信号：**

用户能够使用真实装修资料完成“采集 -> AI 候选提取 -> 人工确认 -> 正式记录归档 -> 搜索 / 目录查询 -> 来源追溯”闭环，且任何未经确认的 AI 内容都不会进入正式知识。

状态：定性信号已确认；定量阈值待补充，见第 10 节。

**建议考虑的衡量方向：**

- 一份真实资料完成确认和归档所需时间。
- AI 提取结果被直接接受、编辑后接受和拒绝的比例。
- 正式记录具有可访问来源的比例。
- 用户一周后能够重新找到并使用记录的比例。
- 已整理记录实际参与候选比较或决策的比例。

## 3. 产品范围与优先级

### 3.1 优先级定义

| 优先级 | 定义 |
|---|---|
| P0 | 验证“采集、提取、确认、归档、搜索、溯源”核心价值 |
| P1 | 完成装修场景中的 Review 与采集整理效率能力（决策、预算暂缓） |
| P2 | 提高整理效率并扩展到其他场景 |
| P3 | 多人协作、平台化和远期能力 |

状态：已确认。2026-08-07 更新：决策、预算/花费、PDF/网页正文解析（合同/报价类）、商品/参数候选对比因使用场景少、复杂度高暂缓；2026-08-09 更新：装修目录模板（K1）、项目首页概览（B5）一并暂缓。

### 3.2 P0 范围

P0 暂定包含：

- 已有账号和密码登录。
- 项目管理。
- 多级知识目录。
- 文字、截图和链接采集。
- 原始来源和附件保存。
- OCR 和结构化信息提取。
- 证据、适用条件、置信度和建议节点。
- 人工编辑、确认和拒绝。
- 正式知识记录及来源追溯。
- 基础关键词搜索。
- 移动端采集与桌面端整理。
- AI Provider 抽象、异步任务和失败重试。

状态：已确认。P0 包含已有账号密码登录，不包含用户自助注册。

### 3.3 P0 明确不做

- 知识图谱可视化。
- 以 AI 聊天为主要入口。
- 视频、音频和聊天记录解析。
- 多人协作和复杂权限。
- 完整财务记账系统。
- 模板市场。
- MCP、Webhook 和开放平台。
- 自动修改正式知识记录。
- 用户自助注册、找回密码和第三方登录。

状态：已确认。

### 3.6 当前阶段暂缓项（2026-08-07、2026-08-09 决定）

以下功能原计划在 P1 推进，因目标用户使用场景少、实现复杂度高或与现有页面重叠，改为暂缓：
不进入近期切片；保留在详细文档中仅作为远期基线，不代表最终不做。

- 最终决策（创建决策、候选方案、理由与约束、关联记录与来源、变更历史）。
- 预算与花费（项目/节点预算、花费记录、凭证附件、层级汇总、超支提醒）。
- PDF 上传与解析、网页正文与元数据抓取（合同 / 报价类）。
- 商品/参数候选对比（依赖决策，一并暂缓）。
- 内置装修目录模板（K1）：使用场景少，模板难以覆盖真实项目差异。
- 项目首页概览（B5）：与现有项目列表、目录与记录页信息重叠。

暂缓期间产品聚焦知识采集与整理；P2/P3 中依赖决策/预算的能力一并延后评估。

### 3.5 功能依赖

```text
已有账号密码登录 / 默认 Workspace
-> Project
-> Node 目录树
-> Source 保存
-> Processing Task
-> Extraction
-> 人工确认
-> Entry 归档与来源关联
-> 搜索与来源追溯
-> Review（P1，已完成）；Decision / Budget（暂缓）
```

已确认规则：

- Source 可以在未选择 Project 时先保存，但生成正式 Entry 前必须确认 Project。
- Node 目录树必须先于 Entry 归档存在；全局采集箱不依赖用户先进入某个 Node。
- 文字 Source 不依赖 OCR，可以先验证 Extraction、人工确认和 Entry 归档流程。
- 图片 Source 在保存成功后再进入 OCR 和 AI 提取；处理失败不影响 Source 本身可访问。
- 搜索依赖 Entry、Node 和 Source 关联数据；P0 优先使用 MySQL 基础能力。
- Review 依赖稳定的 Entry 与 Source 追溯关系，已完成；Decision 和 Budget 同样依赖该追溯关系，但当前暂缓。

已确认：登录是进入产品主界面的独立 P0 前置 Change。账号由部署人员通过交互式 CLI 预置并创建默认个人 Workspace；使用可撤销的数据库 Session 和 HttpOnly Cookie。普通登录为浏览器会话且服务端最长 24 小时，“保持登录”为固定 30 天；退出只撤销当前会话，部署人员重设密码时撤销该账号全部会话。

### 4.3 关键用户故事

- 作为正在装修的个人用户，当我在手机上看到有用的截图、链接或文字时，我希望先快速保存原始来源，从而不因必须立即分类而中断当前任务。
- 作为集中整理资料的用户，当 OCR 和 AI 生成多条候选时，我希望逐条修改、接受或拒绝，从而确保错误内容不会进入正式知识。
- 作为准备购买或施工的用户，当我打开一个知识节点时，我希望看到已确认记录、适用条件和关联来源，从而判断这条经验是否适用于当前情况。
- 作为需要查找历史信息的用户，当我搜索关键词时，我希望按项目、节点、类型和状态筛选，并能回到节点或原始来源，从而验证结论而不是只看到摘要。
- 作为进行 Review 的用户，当系统发现冲突或缺少条件时，我希望对比正式记录和来源并确认修改，从而在不允许 AI 自动改写知识的前提下解决问题。

状态：P0 用户故事已确认；Review 用户故事为 P1 方向已确认。

## 5. 信息架构与导航

### 5.1 全局信息架构

```text
KnowStruct
├── 项目
│   ├── 项目列表
│   └── 项目工作区
│       ├── 目录（默认）
│       ├── 资料（Source 与处理队列）
│       ├── 记录（Entry 聚合列表）
│       ├── Review（P1，当前项目过滤）
│       ├── 决策（暂缓）
│       └── 预算（暂缓）
├── 采集箱（全局 Source 入口，可选项目）
├── 搜索（全局）
├── Review（P1，全局问题聚合）
└── 我的
```

已确认规则：

- 全局导航承载跨项目任务；项目工作区承载项目私有对象。
- 采集箱只有一套数据，提供全局入口和带项目预选的项目内快捷入口。
- 采集时可以暂不选择项目；Extraction 生成正式 Entry 前必须确认项目。
- “资料”和“记录”保持独立：资料表示 Source 及处理状态，记录表示正式 Entry。
- Review 同时提供全局聚合入口和项目内过滤入口，两者使用同一组 Review Finding。
- 决策和预算只在项目内展示，当前阶段暂缓，不进入全局主导航。

状态：已确认。依据：第一版低保真原型及 `docs/prototypes/low-fi/review-decisions.md`。

### 5.2 移动端导航

```text
项目 | 采集 | 搜索 | Review | 我的
```

已确认规则：

- “采集”是移动端主要动作，位于底部导航中间。
- 知识目录属于项目内部，不进入底部导航。
- Review 在 P0 导航中显示 P1 标记，用于确认导航容量，但不承诺 P0 实现 Review 业务能力。

状态：已确认。

以正式 Entry 为主要结果，Source 原文命中作为证据提示；结果可以回到所属节点或原始 Source。无结果时保留关键词和筛选，并提供清除筛选。对应 D06 / M07。

**来源预览：**

桌面端默认使用右侧抽屉保留上下文，同时提供独立详情页；移动端使用整页。来源失效时保留已保存内容和关联关系。对应 D07 / M08。

### 6.4 全局交互原则

- AI 只提出候选内容，不直接覆盖正式记录。
- 涉及正式知识的 AI 操作必须允许用户确认或拒绝。
- 正式记录必须能够追溯到原始来源。
- 长时间任务必须展示状态，并允许失败后重试。
- 移动端优先减少输入步骤，桌面端优先提高批量整理效率。
- 不用知识图谱画布代替清晰的目录和详情导航。
- 采集时可以暂不选择项目，但生成正式 Entry 前必须确认项目。
- AI 候选按条接受或拒绝；同一 Source 的部分候选被拒绝时，只为已接受项创建 Entry。
- Source 处理失败时保留原始内容，并允许从失败步骤重试。

## 8. 领域模型与数据边界

### 8.1 核心数据分层

```text
Source
原始截图、链接、文字或文件

Processing Task
围绕 Source 执行上传、OCR 和 AI 提取的异步任务

Extraction
AI 生成的候选结构化结果

Entry
用户确认后的正式知识记录

Decision
基于多条记录和来源形成的最终决策
```

### 8.2 关键关系

```text
一个 Source 可以产生多个 Extraction
一个 Entry 可以关联多个 Source
一个 Source 可以支持多个 Entry
一个 Decision 可以关联多个 Entry 和 Source
一个 Node 可以包含多个子 Node 和 Entry
预算与花费可以关联 Project 或 Node
```

### 8.3 数据不变量

- AI 生成内容不得直接覆盖原始来源。
- 未经用户确认的 Extraction 不得自动成为正式 Entry。
- 删除来源前必须处理正式记录对该来源的引用。
- 正式记录的来源关系必须可以查询。
- 异步任务重复执行不能生成重复的正式记录。

状态：已确认。

### 8.4 生命周期状态

**Source 状态：**

- 内容状态：保存中 / 已保存 / 来源失效 / 待删除。
- 项目归属：未分配 / 已分配。
- OCR 和 AI 处理状态不直接复用 Source 内容状态，使用独立 Processing Task 表达。

**Processing Task 状态：**

- 待处理 / 上传中 / OCR 处理中 / AI 提取中 / 处理成功 / 处理失败。
- 失败后可以从失败步骤重试；重试不得复制 Source 或已存在的 Entry。

**Extraction 状态：**

- 待确认 / 已接受 / 已拒绝。
- 同一 Source 可以同时存在已接受、已拒绝和待确认的候选。

**Entry 状态：**

- 已归档 / 有冲突。
- 草稿、归档、删除和历史版本的完整生命周期需要在 Entry 相关 Change 中继续明确。

**Review Finding 状态：**

- 待处理 / 已解决 / 已忽略。
- 属于 P1，具体重新打开和批量处理规则在 Review Change 中明确。

**Decision 状态：**

- 草稿 / 已确认 / 已变更 / 已作废。
- 功能实现暂缓（2026-08-07 决定）；状态模型保留为远期基线，变更历史规则待重启时在 Decision Change 中明确。

状态：草案。状态名称已根据低保真原型收敛，但删除、恢复、历史版本和并发重试规则仍需在对应 Change 中定义。

已确认范围（`capture-text-to-entry`，2026-08-05）：Source 内容状态（保存中 / 已保存）与处理状态分离；Processing Task 为待处理 / 处理中 / 处理成功 / 处理失败（单行状态机、attempt_count、失败步骤重试、stale running 超时恢复）；Extraction 待确认 / 已接受 / 已拒绝；Entry 由接受候选创建，默认已归档，保留 extraction 与 entry_sources 关联。删除、恢复、历史版本、Entry 常规编辑和冲突状态仍需在后续 Entry 相关 Change 中明确。

- [ ] Change 中承诺的需求和场景已经实现。
- [ ] 明确排除的功能没有被顺带加入。
- [ ] 正常、空、处理中、失败和重试状态经过验证。
- [ ] 相关自动化测试通过。
- [ ] 前端构建和后端检查通过。
- [ ] 使用真实资料完成至少一次端到端验收。
- [ ] 数据迁移、配置和部署变化已经记录。
- [ ] 用户可见行为与 OpenSpec Specs 一致。
- [ ] 发现的需求变化已反映到本次 Change。
- [ ] Change 已归档，正式 Specs 已更新。

## 12. OpenSpec 项目上下文建议

默认上下文采用“短摘要 + 相关主规格 + 按需章节”方式，避免每个会话全文加载所有产品文档。具体读取顺序和章节路由见 `docs/项目上下文与文档路由.md`，实际规则以根目录 `AGENTS.md` 和 `openspec/config.yaml` 为准。

`openspec/config.yaml` 应保持以下信息类型，而不是复制详细文档全文：

```yaml
context: |
  项目名称：KnowStruct。

  默认读取 AGENTS.md、docs/项目上下文与文档路由.md 和相关主规格。
  长文档仅按路由读取与当前需求相关的章节。

  AI 只能生成待确认候选内容，不得直接覆盖正式知识记录。
  原始来源、AI 提取结果、正式知识记录和最终决策必须分层保存。
  所有正式知识记录必须支持来源追溯。
  P0 使用普通知识目录树，不引入图数据库。
```

实际字段和内容以安装后的 OpenSpec 当前版本配置格式为准。
