# OpenSpec 前置准备基线

## 0. 文档说明

### 0.1 文档目的

本文件用于在项目进入 OpenSpec 功能开发流程前，统一整理产品级背景、范围、优先级、信息架构、交互基线、领域模型、技术约束和验收标准。

它解决两个问题：

1. 为后续每个 OpenSpec Change 提供稳定的全局上下文。
2. 判断某个功能是否已经准备好进入 `proposal -> specs -> design -> tasks -> apply` 流程。

本文件不是详细 PRD，也不要求开发前填完所有远期功能。未确定内容可以保留“待补充”，但进入首个 OpenSpec Change 前，标记为“阻塞”的项目必须明确。

### 0.2 使用方式

- 已确定内容直接填写，并注明依据。
- 尚未确定的内容保留 `_待补充_`，不要用未经验证的内容强行填满。
- 产品级共识写在本文件；单个功能的行为和技术方案写入 OpenSpec Change。
- 当全局导航、核心对象或产品原则变化时，先更新本文件，再更新受影响的 OpenSpec Specs。
- 其他项目可以复制本文件，保留目录后重新填写。

### 0.3 状态标记

| 标记 | 含义 |
|---|---|
| 已确认 | 已形成明确决定，可以作为开发约束 |
| 草案 | 有初步方向，需要在开发前确认 |
| 待补充 | 当前没有足够信息 |
| 不适用 | 当前项目不需要 |

### 1.2 单个功能准备度

每次创建 OpenSpec Change 前检查：

- [ ] 要解决的用户问题清楚且具体。
- [ ] 目标用户和触发场景明确。
- [ ] 本次包含内容明确。
- [ ] 本次明确不做的内容已经列出。
- [ ] 已设置本次 Appetite 或投入边界。
- [ ] 正常流程、空状态、处理中、失败和重试行为已考虑。
- [ ] 涉及的页面和整体信息架构不冲突。
- [ ] 涉及的核心领域对象和数据归属明确。
- [ ] 可以写出可验证的 Given/When/Then 场景。
- [ ] 有相应测试数据或真实验收材料。
- [ ] 知道完成后如何判断“可用”，而不只是“代码写完”。

只有上述项目基本明确后，才建议运行：


## 3. 产品范围与优先级

### 3.1 优先级定义

| 优先级 | 定义 |
|---|---|
| P0 | 验证“采集、提取、确认、归档、搜索、溯源”核心价值 |
| P1 | 完成装修场景中的 Review、决策和基础预算能力 |
| P2 | 提高整理效率并扩展到其他场景 |
| P3 | 多人协作、平台化和远期能力 |

状态：已确认。

### 3.2 P0 范围

P0 暂定包含：

- 项目管理。
- 多级知识目录。
- 文字、截图和链接采集。
- 原始来源和附件保存。
- OCR 和结构化信息提取。
- 证据、适用条件、置信度和建议节点。
- 人工编辑、确认和拒绝。
- 正式知识记录及来源追溯。
- 基础关键词搜索。
- 移动端采集与桌面端整理。
- AI Provider 抽象、异步任务和失败重试。

状态：草案，进入首个 Change 前需确认首版是否包含账户体系。

### 3.3 P0 明确不做

- 知识图谱可视化。
- 以 AI 聊天为主要入口。
- 视频、音频和聊天记录解析。
- 多人协作和复杂权限。
- 完整财务记账系统。
- 模板市场。
- MCP、Webhook 和开放平台。
- 自动修改正式知识记录。

状态：草案。

## 6. 整体布局与交互基线

### 6.1 端侧职责

**移动端重点：**

- 快速上传截图。
- 快速记录文字或链接。
- 查看处理状态。
- 快速确认 AI 提取结果。
- 搜索和查看节点注意事项。

**桌面端重点：**

- 调整知识目录。
- 批量整理资料。
- 编辑复杂结构化内容。
- 处理冲突 Review。
- 比较候选项和形成决策。
- 查看预算统计。

状态：草案。

### 6.2 核心交互流程

**流程 A：采集到正式知识**

```text
输入文字 / 截图 / 链接
-> 保存原始来源
-> OCR 或内容解析
-> AI 结构化提取
-> 建议归档节点
-> 用户编辑、确认或拒绝
-> 生成正式知识记录
```

状态：已确认。

**流程 B：搜索与来源追溯**

```text
输入关键词
-> 查看匹配记录
-> 打开知识节点
-> 查看关联来源
-> 打开原图或原文
```

状态：草案。

**流程 C：Review 到决策**

```text
查看 Review 问题
-> 对比相关记录和来源
-> 接受或拒绝修改建议
-> 补充适用条件
-> 形成或更新决策
```

状态：P1 草案。

### 6.4 全局交互原则

- AI 只提出候选内容，不直接覆盖正式记录。
- 涉及正式知识的 AI 操作必须允许用户确认或拒绝。
- 正式记录必须能够追溯到原始来源。
- 长时间任务必须展示状态，并允许失败后重试。
- 移动端优先减少输入步骤，桌面端优先提高批量整理效率。
- 不用知识图谱画布代替清晰的目录和详情导航。

## 8. 领域模型与数据边界

### 8.1 核心数据分层

```text
Source
原始截图、链接、文字或文件

Extraction
AI 生成的候选结构化结果

Entry
用户确认后的正式知识记录

Decision
基于多条记录和来源形成的最终决策
```

状态：已确认。

### 8.2 关键关系

```text
一个 Source 可以产生多个 Extraction
一个 Entry 可以关联多个 Source
一个 Source 可以支持多个 Entry
一个 Decision 可以关联多个 Entry 和 Source
一个 Node 可以包含多个子 Node 和 Entry
预算与花费可以关联 Project 或 Node
```

状态：草案。

### 8.3 数据不变量

- AI 生成内容不得直接覆盖原始来源。
- 未经用户确认的 Extraction 不得自动成为正式 Entry。
- 删除来源前必须处理正式记录对该来源的引用。
- 正式记录的来源关系必须可以查询。
- 异步任务重复执行不能生成重复的正式记录。

状态：草案。

```markdown
-

-

-

-

- 
```

```text
/opsx:explore
```
