# KnowStruct 项目上下文与文档路由

## 1. 用途

本文件是新会话和 OpenSpec Change 的默认短上下文。它不替代详细产品文档，而是说明稳定共识、事实来源和何时读取哪些章节。

2. `openspec/config.yaml`。
3. 本文件。
4. 与当前需求相关的 `openspec/specs/<capability>/spec.md`。

不要默认全文读取以下长文档：

- `docs/OpenSpec前置准备基线.md`

需要细节时，按第 7 节路由到相关章节。

## 2. 产品摘要

KnowStruct 是面向经验型知识和复杂决策的响应式 Web 应用。它把截图、链接、文字和文件等零散资料，通过 AI 辅助处理和人工确认，沉淀为可维护、可检索、可审查、可追溯的结构化知识与决策。

首个真实场景是新房装修，核心闭环是：

```text
采集原始资料
-> OCR 或内容解析
-> AI 生成结构化候选
-> 用户编辑、确认或拒绝
-> 归档为正式记录
-> 搜索与来源追溯
-> Review（已完成）；决策和预算（暂缓）
```

产品价值不是单纯保存信息，而是降低整理成本，并让后续判断能够回到证据和适用条件。

## 3. 当前阶段与顺序

P0 用真实装修资料验证“采集、提取、确认、归档、搜索、溯源”。当前建议按以下垂直切片推进：

1. `login-with-password`：已完成、已归档，主规格已同步。
2. `create-project-and-tree`：已完成、已归档，主规格已同步。
3. `capture-text-to-entry`：已完成、已归档，主规格已同步（采集箱 / 处理队列 / AI 候选 / 逐条确认 / Entry 创建）。
4. `upload-image-and-ocr`
5. `extract-and-confirm-entry`
6. `search-and-trace-source`

每次开始前仍需运行 `openspec list` 并检查 `openspec/specs/`，不要仅依赖本节状态。

P0 不包含用户注册、找回密码、第三方登录、图谱可视化、AI 聊天主入口、多人协作、复杂权限、完整财务系统或平台化能力。

决策、预算/花费、PDF/网页正文解析（合同/报价类）当前暂缓（2026-08-07 决定）：目标场景使用少、复杂度高，产品先聚焦知识采集与整理。

## 4. 稳定领域边界

```text
Workspace
  Project
    Node
      Entry
      Source
      Attachment
      Decision
```

知识处理必须保持以下分层：

- `Source`：用户提供的原始截图、链接、文字或文件。
- `Processing Task`：上传、OCR、AI 提取等异步执行状态。
- `Extraction`：AI 生成且尚未确认的候选内容。
- `Entry`：用户确认后的正式知识记录。
- `Decision`：基于多条 Entry 和 Source 形成的最终选择（领域概念保留；决策功能暂缓实现）。

核心不变量：

- AI 候选不得直接成为或覆盖正式 Entry。
- 正式 Entry 必须能够查询关联 Source。
- 一个 Source 可产生多个 Extraction，也可支持多个 Entry。
- 一个 Entry 可关联多个 Source。
- 异步任务重试不得复制 Source 或已存在 Entry。
- 删除 Source 前必须处理正式记录的引用关系。
- P0 的 Node 是普通多级目录树，不是图数据库节点。

## 5. 信息架构与端侧职责

全局导航承载跨项目任务：项目、采集、搜索、Review、我的。项目内部承载目录、资料、记录，以及 Review（已完成）；决策和预算（暂缓）。

移动端与桌面端使用同一套响应式 Web 技术和同一后端：

- 移动端：快速采集截图、文字和链接，查看状态，逐条确认候选，搜索和整页查看来源。
- 桌面端：维护目录，批量整理，对照来源与候选，处理 Review（决策和预算暂缓）。

“资料”表示 Source 与处理状态；“记录”表示正式 Entry，二者不得混用。采集时可以暂不选择项目，但创建正式 Entry 前必须确认项目。

## 6. 技术与交付基线

- React 19 + TypeScript + Vite + Tailwind CSS 4。
- FastAPI + Pydantic v2 + async SQLAlchemy + Alembic。
- MySQL 8.0+，生产目标为 ECS + Nginx + RDS；附件使用 OSS。
- AI 能力通过可替换 Provider 接入，OCR 和 AI 处理需要明确状态、失败和重试。
- 业务数据必须按当前认证用户和默认 Workspace 隔离。
- 持久化结构变化必须提供迁移和真实 MySQL 验证。
- 完成标准包括自动化测试、构建与 lint、真实流程验收、规格同步和归档。

## 8. 事实来源与冲突处理

按以下方式判断信息用途：

1. 当前用户指令和当前 active Change：本次目标与范围。
2. `openspec/specs/`：已经实现并生效的行为事实。
3. `openspec/config.yaml` 和本文件：稳定项目约束与默认上下文。
4. 三份详细文档及低保真原型：未来范围、细节基线和待决策事项。
5. `openspec/changes/archive/`：历史理由和变更记录。

若主规格与详细产品基线冲突，不要静默选择一方；先指出冲突，再通过 explore 或 update-change 明确是否修改当前行为或产品基线。

## 9. 新 Change 最小准备卡

进入 propose 前至少明确：

- 用户在什么场景遇到什么问题。
- 完成后用户能得到什么结果。
- Appetite 或投入上限。
- 本次包含与明确不包含的内容。
- 正常、空、处理中、失败和重试状态。
- 涉及的页面、领域对象、数据归属与删除影响。
- 可验证场景、测试数据和真实验收方式。

信息不足时先 explore，不要直接实现或顺带扩大到后续优先级。
