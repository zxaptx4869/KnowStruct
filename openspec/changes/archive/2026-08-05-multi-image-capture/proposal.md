## Why

一张图经常表达不完整（多角度、多页截图、一组对比图），当前一次只能上传一张，用户需要拆成多条采集，后续确认与归档时也难对照。同时文字 / 链接 / 图片的采集动作语义不统一（图片无独立提交按钮），容易造成"以为没点上的"困惑。本切片把图片采集升级为"一条最多 3 张、客户端攒选、点一次'开始提取'批量入队"，并把三种方式的提交按钮统一为"开始提取"。

## What Changes

- Source 附件从单列拆为子表 `source_attachments`：一条图片采集最多 3 张，带排序与元数据；原单图数据迁移保留。
- 图片采集改为客户端攒选：相册多选 / 拍照追加 / 开始前可移除，预览确认后点"开始提取"一次提交（原子性：任一文件校验失败则整批拒绝，不建 Source）。
- 三种方式提交按钮统一为"开始提取"：文字 / 链接保持"提交即入队"的现有行为，仅统一文案；图片由"选图即自动上传"改为"选齐后手动开始"。
- OCR 循环识别全部附件，按图序合并成一份正文（标注"图 1 / 图 2"）再进入 AI 提取；任一张失败整条任务失败、从 OCR 阶段重试，不重复上传。
- 送审前生成识别副本：最长边压缩到 2048px（JPEG/WebP 质量约 80），原图保留用于预览与存档，降低豆包按 token 计费的成本与延迟。
- 上传大小与格式限制不变（单张 ≤10MB、JPG/PNG/WebP、4096px），批量总张数 ≤3。

## Capabilities

### New Capabilities
- 无新增能力；能力变更并入现有规格。

### Modified Capabilities
- `image-upload-and-ocr`: 附件模型改为多附件子表；上传接口支持批量与原子校验；OCR 流水线支持多图循环与合并正文；送审前压缩副本；采集入口改为"选齐后点开始提取"。
- `inbox-processing`: 采集入口的统一"开始提取"按钮语义；图片采集的客户端多选与开始前移除；失败保留所选图片与项目选择。

## Impact

- 后端：alembic 0005（`source_attachments` 表 + 单图数据回填）；`inbox` 上传接口改为 `files[]`；`create_image_source` 批量落盘；OCR 服务循环合并；新增图片压缩工具（Pillow）；响应模型 `attachment` 扩展为附件列表（兼容旧字段）。
- 前端：图片采集多选与预览条（缩略图、移除、计数上限）、"开始提取"按钮统一文案、详情页多图预览；`inbox` 类型更新。
- 验证：后端 pytest + ruff；前端测试 / lint / build；OpenSpec 严格校验；MySQL 迁移与批量上传冒烟；浏览器桌面与 390px 验收（相册多选 / 拍照追加 / 移除 / 开始提取）。
