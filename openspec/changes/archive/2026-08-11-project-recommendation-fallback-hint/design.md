## Context

未选项目采集时，AI 项目推荐在低置信度（< 0.6）、调用失败或超时的情况下返回「不推荐」，
`recommend_source_project` 静默返回且不落库任何标记（`recommended_at` 保持为空），
采集与提取照常进行。用户随后进入逐条确认页 `/inbox/:id`，归档项目下拉旁只有空选项
"请选择项目"，没有任何说明，容易误以为推荐功能漏掉了。主规格
`ai-archive-suggestion` 已要求该场景「提示确认时手动选择」，本次补齐该提示。

## Goals / Non-Goals

**Goals:**

- 确认页（采集后落地页）在推荐无法得出时给出可读提示，说明需要手动选择归档项目。
- 仅前端改动，不改后端接口、数据模型，无数据库迁移。
- 提示只在语义准确时出现：处理完成、Source 仍未分配、无推荐结果、工作区存在项目。

**Non-Goals:**

- 不新增后端字段记录推荐失败原因（如需展示模型理由，另行立项）。
- 不在采集箱列表行增加常驻标记（会为所有未分配资料制造噪音）。
- 不实现「使用/忽略」按钮（inbox-processing 主规格的相邻缺口，不在本次范围）。
- 不处理工作区没有项目时确认页无法接受候选的既有边界。

## Decisions

### 1. 纯前端推断推荐是否失败，不新增后端标记

提示条件为：

```text
source.processing_state not in ('processing', 'failed')
&& source.project_id == null
&& source.recommended_project_id == null
&& 当前工作区项目数 > 0
```

依据：当前流程保证「不在处理中/失败 ⇒ 推荐已尝试」——文字/链接在采集提交时同步推荐，
图片在 `process_source_extraction`（OCR 之后）补调推荐，任务成功并产生候选后进入
`pending_confirm`。因此不再处理中的 Source 仍未分配且无推荐结果，必然对应低置信度、
模型不推荐或调用失败。工作区只有一个项目时会自动推荐（不调模型），不会进入此分支。

备选：后端新增推荐结果状态列（区分 matched / low_confidence / failed / no_projects）
并把模型理由落库。优点是可展示「内容同时涉及多个项目，无法可靠判断」等理由，并能精确
区分失败与低置信；代价是需要迁移 0019、真实 MySQL 验证与接口字段扩展。对本次「一句提示」
的小完善，收益不匹配成本，故不采用。

### 2. 提示位置：确认页归档项目下拉旁

采集提交成功后立即跳转 `/inbox/:id`（即 SourceConfirmPage），因此该页面就是用户感知的
"采集页"。提示放在项目下拉的同一 `compact-project-field` 区域内、成功推荐 banner
（`recommend-banner`）的对应位置，桌面与移动共用同一响应式布局，无需新增断点样式。

备选：采集箱列表行 badge——用户在队列中能一眼看到，但对所有未分配资料都展示会产生
噪音，且无法表达"已尝试但失败"与"还没处理"的区别，弃用。

### 3. 文案与可访问性

文案「AI 未能可靠判断归档项目，请手动选择」，与节点建议降级文案
「AI 未能可靠判断归档节点，请手动选择」保持一致的措辞风格；使用 `role="status"`，
复用 `recommend-banner` 样式以区分于普通表单提示。

## Risks / Trade-offs

- [推断依赖"处理完成 ⇒ 已尝试推荐"的现状] → 当前文字/链接/图片三条路径均满足；若未来
  推荐被延迟到确认阶段执行，需重新评估该条件。在规格场景中写明触发条件，约束未来改动。
- [推荐失败的任务被重试后可能重新推荐] → 正是期望行为：`recommended_at` 为空时重试会
  重新尝试，若成功则 banner 取代提示，不会固化误判。
- [工作区 0 项目时不显示提示] → 提示会误导（无可选对象），不显示是正确取舍；确认页
  "必须选项目才能接受"的既有拦截属于独立边界，不在本次范围。

## Migration Plan

无数据库迁移。部署无先后顺序要求；前端发布后提示即生效，回滚仅需还原前端改动。
