## Context

项目记录列表由 `GET /projects/{id}/entries` 提供，前端整量加载后按节点/类型做客户端过滤；整理模式（桌面端）支持多选批量移动/删除。采集箱已有服务端关键词查询的先例（`q` 参数 + LIKE 转义）。

## Goals / Non-Goals

**Goals:**
- 记录多时可按关键词快速定位，查询发生在服务端（而非只筛已加载数据）。
- 通配符按字面匹配，与全局搜索一致；匹配数与总数分离返回。
- 保持移动端「无多选批量、无搜索框」的既有边界。

**Non-Goals:**
- 不做全局搜索聚合、不做高亮、不改记录列表 200 条上限、不改节点级记录列表。

## Decisions

1. **服务端过滤**：`q` 参数在 `list_project_entries` 内构造 WHERE 条件，`escape_like` 转义 `%`/`_`/`\` 并按 `ESCAPE '\'` 匹配；与采集箱 `q` 与全局搜索语义一致。
2. **matched_count 独立统计**：复用同一 filters 做 `COUNT`，与 `total`（全量记录数）分开返回，避免前端用「加载条数」冒充匹配数（列表有 200 条上限）。
3. **查询键入参**：`useProjectEntries(projectId, q?)` 将 `q` 纳入 queryKey，提交式搜索（与采集箱一致），`清除` 重置为全量。
4. **移动端边界**：搜索框仅在 `!mobile` 渲染；批量工具栏在 `max-width: 767px` 下 CSS 隐藏，与「移动端无勾选入口」互为兜底。

## Risks / Trade-offs

- [匹配数超过 200 条时 items 截断] → 头部显示 matched_count 与实际加载条数分离，用户可见差异由既有上限说明；如需完整分页另立切片。
- [LIKE 查询在超大数据量下的性能] → 项目记录量级受 200 条展示上限约束，本期可接受；后续可加索引或走全局搜索。

## Migration Plan

无迁移。前后端同版发布，旧响应新增 `matched_count` 字段，前端按缺省回退（`?? records.length`）兼容渐进发布。
