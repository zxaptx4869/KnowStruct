## Context

KnowStruct 当前是 React SPA 与 FastAPI 骨架。前端所有业务路由均可直接访问；后端仅有健康检查，数据库 Session 和当前用户依赖仍是 TODO。仓库有 SQLAlchemy、Alembic 和 `python-jose` 依赖，但尚未初始化 Alembic 目录，也没有用户、工作区或认证会话模型。

P0 已确认只支持已有账号和密码登录，不提供注册、找回密码或第三方登录。桌面和移动低保真原型已经确认相同的登录字段、保持登录、统一错误和成功进入项目列表行为。当前部署目标为单体 FastAPI + MySQL，前后端生产环境同源，后续 PWA 也继续使用同一 Web 会话。

## Goals / Non-Goals

**Goals:**

- 建立安全、可测试、可立即撤销的账号密码认证。
- 为每个预置用户建立稳定的默认个人工作区边界。
- 在普通浏览器、移动浏览器和后续 PWA 中复用同一 Cookie 会话。
- 建立后续领域模型可复用的数据库迁移、请求 Session 和当前用户依赖。
- 完整覆盖登录、恢复、过期、路由保护和退出状态。

**Non-Goals:**

- 用户注册、自助找回或修改密码、邮箱或手机号验证。
- OAuth、第三方登录、MFA、成员角色和复杂权限。
- 多工作区切换、会话设备列表或“退出所有设备”界面。
- Project、Node 等业务模型和 API。
- PWA 安装、原生 Android/iOS 包装或离线认证。

## Decisions

### 1. 使用数据库不透明 Session，不使用前端可读 JWT

登录成功后生成至少 256 bit 的随机 Token，Cookie 保存原始 Token，数据库只保存 Token 的 SHA-256 摘要。每次认证通过摘要定位 `auth_sessions`，检查撤销和固定过期时间，再加载用户与默认工作区。

选择该方案是因为 P0 规模下每次请求一次索引查询成本可接受，同时退出和管理员重设密码可以立即撤销会话。JWT 放入 `localStorage` 会扩大 XSS 后的凭据暴露面；仅清除 JWT Cookie 又无法让已泄露 Token 立即失效。现有 `python-jose` 和 JWT 配置属于未使用骨架，可在实现时移除或保留为未启用依赖，但不得驱动本次设计。

### 2. Cookie 根据“保持登录”使用两种固定期限

- 未勾选：Cookie 不设置 `Max-Age`/`Expires`，浏览器关闭后通常移除；服务端仍设置创建后 24 小时的硬过期上限。
- 已勾选：Cookie 和服务端会话固定 30 天过期。
- 普通请求不滚动延长过期时间。后续如需滑动续期，应作为独立需求评估。

Cookie 名使用 `knowstruct_session`，路径限制为 `/`，生产环境启用 `Secure`、`HttpOnly` 和 `SameSite=Lax`。本地 HTTP 开发仅允许通过显式开发配置关闭 `Secure`。

### 3. 账号由 CLI 预置，并事务性创建默认工作区

提供后端 CLI 子命令创建账号和重设密码。CLI 通过隐藏输入读取并二次确认密码，不接受把明文密码作为普通命令行参数。账号标识去除首尾空白并进行大小写无关规范化；密码内容不做 trim。

创建账号时在一个事务内写入：

- `users`: UUID、唯一规范化 `login_name`、密码哈希、时间戳。
- `workspaces`: UUID、唯一 `owner_user_id`、默认名称“我的工作区”、时间戳。

P0 使用 `owner_user_id` 表达一人一个默认个人工作区，不提前引入成员关系和角色表。后续多工作区属于 P3，可通过迁移引入 membership 模型。

密码使用 Argon2id 哈希，接受 12 至 128 个字符，验证时保持用户输入原样。管理员重设密码后撤销该用户所有 Session，但不提供用户可见的找回密码流程。

### 4. 会话模型保持最小且支持撤销

`auth_sessions` 包含 UUID、`user_id`、唯一 `token_hash`、`expires_at`、可空 `revoked_at` 和创建时间。认证只接受未撤销且未过期记录。过期记录可在认证时惰性拒绝，后续再通过维护任务批量清理；清理不是请求正确性的前提。

允许同一用户拥有多个设备会话。普通退出只撤销当前记录；密码重设撤销该用户全部记录。

### 5. API 契约围绕 Cookie 会话

- `POST /api/auth/login`: 接收 `account`、`password`、`remember_me`；成功设置 Cookie 并返回当前用户和默认工作区。
- `GET /api/auth/me`: 返回当前用户和默认工作区；无效会话返回 401 并清 Cookie。
- `POST /api/auth/logout`: 撤销当前 Session、清 Cookie，设计为幂等操作。

健康检查和登录建立为公开 API；其他业务 API 通过 `get_current_user` 或更高层的工作区依赖保护。认证错误使用稳定错误代码，前端显示统一文案，不根据账号是否存在改变用户可见结果。

### 6. Cookie 认证采用同源请求和 Origin 校验

前端 API 客户端统一使用 `credentials: "include"`。生产前后端保持同源；开发环境继续通过 Vite `/api` 代理访问后端。所有使用 Cookie 认证的 POST、PUT、PATCH、DELETE 请求校验 `Origin` 是否属于配置的可信来源，避免依赖 CORS 作为 CSRF 防护。

登录接口默认按客户端 IP 限制为每分钟 10 次请求，并允许通过配置调整。由于当前仓库没有共享限流设施，第一版在应用入口提供单实例保护，并在 ECS/Nginx 部署配置中对 `/api/auth/login` 设置第二层限制；未来多进程或横向扩展前必须迁移到共享限流存储。统一错误和 Argon2id 仍是独立的防护层。

### 7. 前端使用认证启动状态和路由守卫

新增独立 `/login` 路由。应用启动时调用 `/api/auth/me`，认证状态为 `checking` 时展示稳定加载状态，不渲染业务页面。未认证访问业务路由时跳转 `/login`，并只保存站内相对目标；成功登录后返回该目标，否则进入项目列表。已认证访问 `/login` 直接进入项目列表。

401 由认证层统一清理客户端用户状态并跳转登录；表单级 401 保留在登录页显示统一凭据错误。桌面与移动使用同一组件和状态逻辑，通过响应式样式匹配 D00/M00。

## Risks / Trade-offs

- [每个认证请求增加一次数据库查询] → `token_hash` 建唯一索引，并在 P0 真实负载后再评估短时缓存。
- [服务端 Session 表持续增长] → 认证严格按过期时间拒绝，预留按 `expires_at` 删除过期记录的维护命令或定时任务。
- [单实例应用限流无法跨 worker 精确共享] → Nginx 增加入口限流；扩容前迁移到共享限流存储。
- [Cookie 认证存在 CSRF 风险] → SameSite、可信 Origin 校验、同源部署共同防护，不开放宽泛生产 CORS。
- [账号无自助恢复入口] → 提供部署人员密码重设 CLI，并明确其会撤销全部会话。
- [默认工作区模型未来需要支持协作] → P0 保持单所有者模型；P3 引入 membership 时通过显式迁移演进。
- [数据库基础设施扩大首个 Change] → Appetite 限制为 5 至 7 个工作日，不纳入 Project/Node 或视觉扩展。

## Migration Plan

1. 初始化 Async SQLAlchemy Engine、请求 Session 和 Alembic 环境。
2. 增加用户、工作区和认证会话模型及首个迁移，在空数据库和现有开发数据库分别验证升级。
3. 部署后端认证 API 和 CLI，运行迁移并创建首个账号；确认健康检查和账号登录后再部署前端路由保护。
4. 部署前端登录页与认证启动逻辑，验证桌面、移动浏览器和刷新恢复。
5. 生产发布前配置 HTTPS、安全 Cookie、可信 Origin 与 Nginx 登录限流。

回滚应用时保留新增表，避免删除账号数据；先回滚前端路由保护，再回滚后端代码。仅在确认没有需保留的账号和会话数据时执行迁移 downgrade。
