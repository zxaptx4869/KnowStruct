## Context

`password-authentication` 已经提供当前用户、默认个人 Workspace 和受保护 API 上下文，但仓库中还没有 Project / Node 持久化模型或业务 API。前端的项目、项目详情和节点页仍是未接入数据的占位实现；`useProjects` 也尚未被页面使用。现有 `backend/app/utils/tree.py` 以节点名称组成物化路径，改名或移动会要求重写整个子树，不适合本 Change 已确认的高频目录维护行为。

本 Change 同时跨越 MySQL 数据结构、FastAPI 业务边界、React 响应式布局和树形交互。它必须保持 P0 普通目录树、当前 Workspace 隔离、桌面整理优先与移动轻量维护的已确认产品边界。

## Goals / Non-Goals

**Goals:**

- 建立 Workspace -> Project -> Node 的持久化所有权边界，为后续 Source 分配和 Entry 归档提供稳定外键。
- 交付项目 CRUD、四种状态和最多 6 层的目录增删改查、移动与同级排序。
- 在服务端强制树完整性、同级名称唯一性和 Workspace 隔离，不信任前端传入的归属信息。
- 交付桌面三段式目录工作区与移动端逐级目录页，覆盖空、加载、提交、失败和重试状态。
- 通过 SQLite 快速测试、一次可丢弃 MySQL `_test` 迁移 / 业务验证和 390px / 桌面浏览器验收保护业务与布局。

**Non-Goals:**

- 不产生 AI 目录候选，不引入模板、图数据库、跨项目关系或节点版本。
- 不实现 Source、Extraction、Entry、Decision 或它们的聚合数量；节点详情只承载目录信息与子节点。
- 不实现项目归档 / 恢复、回收站、复制、导入、最近活动、多工作区或多人权限。
- 移动端不提供拖拽、批量操作或复杂结构整理。

## Decisions

### 1. Project 和 Node 使用关系型邻接表

`projects` 保存 `workspace_id`、名称、目标、背景、状态和时间戳。`nodes` 保存 `project_id`、可空 `parent_id`、名称、标准化名称、说明、同级 `sort_order` 和时间戳。Node 通过自关联表达层级，面包屑由当前节点的父链计算。

选择邻接表是因为 P0 树上限只有 6 层，项目内可一次读取节点并在前端建树；改名不会更新后代，移动也只修改目标节点和受影响的同级排序。不选择名称物化路径，因为名称不应成为稳定身份；不选择 closure table，因为对当前深度和查询规模过重。

项目状态持久化为 `planning`、`active`、`paused`、`completed`，服务端和数据库约束拒绝其他值。状态不改变写入权限。

### 2. 同级唯一与排序由服务端事务维护

节点名称在去除首尾空白后保存，并以标准化名称在同一 Project + 父节点范围内比较。数据库使用非空的同级作用域键区分项目根层与普通父节点，并与 `normalized_name` 组成唯一约束，避免 MySQL 中可空 `parent_id` 允许重复根名称。

`sort_order` 是同级非负整数。创建默认追加到同级末尾；移动请求接收新父节点和目标位置，在单个事务中锁定相关同级集合、检查循环 / 跨项目 / 深度，再重排旧与新同级。不使用分数排序键，避免 P0 引入精度与重平衡复杂度。

### 3. API 始终从认证上下文推导 Workspace

项目 API 使用 `/api/projects`、`/api/projects/{project_id}`；目录 API 使用 `/api/projects/{project_id}/nodes`、`/api/projects/{project_id}/nodes/{node_id}` 和显式的 `.../{node_id}/move` 操作。客户端不能提交 `workspace_id`；服务端查询首先用 `AuthContext.workspace.id` 限定 Project，再在该 Project 下查询 Node。

未认证请求沿用 `401`；不存在或其他 Workspace 的对象统一返回 `404`；同级重名、超深度、循环、跨项目移动和删除引用冲突返回稳定业务错误码的 `409`。Pydantic 处理长度和必填验证。

### 4. 读取整个项目的扁平节点集，前端按 ID 建树

P0 目录规模有限，`GET /projects/{id}/nodes` 返回按父与 `sort_order` 稳定排列的扁平节点集。前端用 `id` / `parent_id` 组织树和面包屑，React Query 以 Project ID 作为缓存边界。项目列表的节点总数由查询实时聚合，不冗余保存；Entry / Source 数量不在本 Change 返回。

此选择比每层懒加载更简单，也能在移动前端即时检测目标是否为后代；如果真实项目的节点规模后续超出可接受范围，再单独引入分页或懒加载。

### 5. 桌面端拖拽是显式移动命令的交互层

桌面项目页使用“全局导航 + 280px 目录树 + 内容区”，使用 `@dnd-kit` 提供拖拽感知和可排序列表。节点菜单另提供明确的“移动到…”和位置选择，作为键盘用户、自动化测试和拖拽不便场景的等价通道。拖拽和菜单最终调用同一 move API。

移动端在项目下先展示当前层节点列表，点击后逐级进入，用页头返回和面包屑保持上下文；仅暴露新增子节点、改名和说明编辑，不注册拖拽交互。

### 6. 结构写入以服务端结果为准，失败后不保留乐观树

表单提交时保留输入并阻止重复点击。项目 / 节点创建、移动和删除不对树结构做无法回滚的乐观更新；成功后更新或失效 React Query 缓存。网络结果不确定时先重新拉取权威列表，不自动重放写请求；已知失败保留对话框和输入，由用户修正或重试。

### 7. 删除是受保护的硬删除，保留未来引用阻断点

P0 不建立归档或回收站状态。用户确认后，项目删除在一个事务中级联删除其目录；节点删除级联删除选定的空子树。删除服务在执行前经过“是否存在受保护内容引用”检查边界；本 Change 没有 Source / Entry / Decision，因此默认没有阻断项，后续引入这些对象时必须在该边界注册引用检查，并以 `409` 阻止破坏溯源的删除。

该方案比现在引入软删除更符合 8 日 Appetite，同时不会把尚未定义的恢复、唯一性和查询语义隐性带入 P0。

## Risks / Trade-offs

- [一次读取全树在超大项目中可能变慢] -> 对 `project_id`、`parent_id`、`sort_order` 建索引，用真实验收目录记录节点量；达到实际瓶颈后再引入懒加载。
- [并发移动可能产生排序竞争] -> MySQL 事务锁定受影响同级集合，每次移动后重排为连续整数；冲突时返回错误并重拉权威树。
- [拖拽树的可访问性和移动端一致性有限] -> 保留等价的节点菜单移动通道，移动端明确不承诺结构整理。
- [硬删除无法恢复] -> 二次确认显示项目名或子树节点数，在服务层保留内容引用阻断边界；归档 / 恢复留给 P1。
- [同级作用域键是冗余数据] -> 只在服务层统一构造，迁移建立唯一约束，并用移动和并发重名测试防止失配。
- [8 日 Appetite 与树形拖拽的打磨成本可能冲突] -> 优先交付正确移动、清晰放置指示和菜单备用通道；名称筛选、动画和聚合摘要是明确的首批削减项。

## Migration Plan

1. 新增 `projects` 和 `nodes` 表、状态约束、外键、同级名称唯一约束与树查询索引；现有 Workspace 不需要回填项目。
2. 在空 SQLite 测试库和可丢弃 MySQL `_test` 数据库执行 upgrade，验证外键、唯一性、级联删除和 downgrade。
3. 后端 API 与前端页面可同版发布；前端在 API 失败时展示可重试状态，不依赖预置 Project。
4. 回滚应先回滚应用，确认无需保留新项目 / 目录数据后再 downgrade；downgrade 会删除两张新表，必须仅在明确接受数据丢失的回滚中执行。
